Guía de estilo · Propuesta de mejora

Bajar el volumen de la interfaz

Análisis del frontend actual (Angular 21 + Material 3) y propuesta v2.1 centrada en un problema concreto: la tipografía y los campos de formulario se ven demasiado grandes para un sistema de trabajo diario. La marca (paleta, tono, tipos) no se cuestiona: se afina para que respire mejor.

Alcance: este documento es solo una propuesta. No se modificó ningún archivo de src/frontend. Los bloques de código son referencia para una futura sesión de implementación. Complementa —no reemplaza— a src/Guia_de_estilo/index.html (guía v2.0 vigente).

00Resumen ejecutivo

Qué está pasando, por qué, y qué se propone hacer.

El síntoma

Todo el chrome de la aplicación —campos de texto sobre todo, pero también filas de tabla, botones y encabezados— ocupa más espacio del que un usuario de mesón espera. En una pantalla de listado con búsqueda apenas entran 6–8 filas antes de hacer scroll; un formulario de alta de cliente (11 campos) no cabe en un alto de viewport estándar.

La causa raíz (no es el font-size suelto)

El tema declara density: 0 y usa la escala tipográfica M3 por defecto (typography: 'IBM Plex Sans' sin sobrescribir roles). Ambas cosas están calibradas por Google para experiencias táctiles / mobile-first: texto de input de 16 px, campos de 56 px de alto, filas de tabla de 52–56 px. En un back-office de escritorio, denso en datos, eso se percibe como "inflado".

La propuesta en una línea

Adoptar densidad negativa (-2 global, -3 en tablas) + una escala tipográfica compacta (input 14 px en escritorio / 16 px en móvil, cuerpo 14, H1 24) mediante overrides de tokens en styles.scss / theme-tokens.scss. Cero cambios de color, familia tipográfica o tono. Cero cambios feature por feature.

01Diagnóstico

Lo que se encontró leyendo styles.scss, theme-tokens.scss, index.html y los .scss de features.

Lo que ya está bien resuelto

  • Sistema de tokens ordenado: --mat-sys-* para roles M3, --opt-* para color con significado, escalas de espaciado/radio/elevación/movimiento.
  • Modo claro/oscuro completo, con prefers-reduced-motion respetado.
  • Familias tipográficas con buen soporte de tildes/ñ y fallback de sistema (IBM Plex Sans / Mono, Fraunces).
  • Contrastes WCAG ya calculados y documentados; estado nunca comunicado solo por color.
  • Componentes compartidos (app-page-header, app-empty-state, app-list-skeleton) — un solo lugar donde ajustar.

Lo que causa la sensación de "todo grande"

A · Densidad Material sin tocar

mat.theme((… density: 0 …)). La escala de densidad de Material va de 0 a -5. 0 es el máximo confort táctil. Un ERP de escritorio suele vivir en -1 a -3.

Efecto en density: 0: form-field ≈ 56px, botón ≈ 40px, fila de tabla ≈ 52–56px.

B · Escala tipográfica M3 stock

Sin overrides de roles, el texto dentro de un mat-form-field es body-large = 16px / 24 / +0.5 tracking. La etiqueta flotante arranca también en 16 px. Las celdas de tabla usan body-medium 14 px, correcto, pero conviven con inputs de 16.

C · Alto fijo del campo + padding interno

El alto de 56 px viene de densidad + body-large. Con etiqueta flotante + mat-hint + mat-error, cada campo reserva ~84 px de alto total. En un formulario de 11 campos son ~920 px solo de campos.

D · Ritmo vertical generoso

.contenido { padding: 24px }, page-header con margin-bottom: var(--opt-space-lg) (24), H1 a 27 px con su propio margin. Sumado, el contenido útil empieza ~110 px por debajo del borde de la toolbar.

Conclusión del diagnóstico: no hay font-size "mal puestos" que corregir uno por uno. El tamaño percibido es una consecuencia sistémica de dos decisiones globales (densidad + escala M3 por defecto). Se corrige en el mismo lugar donde se originó: el mat.theme() y un puñado de tokens en styles.scss.

02Densidad de Material

El interruptor más eficaz: un solo parámetro que reescala inputs, botones, tablas, chips y menús a la vez.

Componentedensity: 0 (hoy)density: -2density: -3Recomendado OPT
Form field (alto)56 px44 px40 px-2 (44 px)
Botón (alto)40 px32 px28 px-2 (32 px)
Fila de tabla52 px44 px40 px-3 en tabla (40 px)
Ítem de lista / menú48 px40 px36 px-2 (40 px)
Chip32 px28 px24 px-2 (28 px)

Estrategia recomendada: densidad mixta

  • Global -2 en mat.theme(): buen equilibrio entre compacto y cómodo para formularios de mesón, sin llegar a lo "apretado". Mantiene el área de toque de los mat-icon-button en ≥40 px si se conserva su hit area.
  • -3 localizado en mat-table vía mat.table-density(-3): las tablas son la vista más densa en datos y las que más se benefician de filas de 40 px. No afecta a los formularios.
  • No pasar de -3 en ninguna zona: por debajo se compromete el área de toque en tablets y el confort de lectura prolongada.
// styles.scss — dentro del bloque html { @include mat.theme( … ) }
density: -2,   // hoy: 0

// …y, fuera del mat.theme(), densidad extra solo para tablas:
.mat-mdc-table {
  @include mat.table-density(-3);
}

Nota: verificar la firma exacta del mixin de densidad para la versión de Angular Material del proyecto (21). En algunas versiones es mat.table-density(...), en otras se aplica vía mat.table-overrides o un mat.theme anidado con solo density.

04Inputs y formularios

El punto que motivó esta revisión. Combina lo de §2 y §3, más ajustes propios del mat-form-field.

Antes (por campo)

  • Alto del control: 56 px
  • Texto: 16 px
  • Etiqueta flotante: 16 → 12 px
  • Reserva total con hint/error: ~84 px
  • Formulario de 11 campos: ~920 px

Después (por campo)

  • Alto del control: 44 px (density -2)
  • Texto: 14 px escritorio / 16 px móvil
  • Etiqueta flotante: 13 → 11.5 px
  • Reserva total con hint/error: ~64 px
  • Formulario de 11 campos: ~700 px (−24 %)

Ajustes finos del mat-form-field

  • Subscript sizing: reservar una sola línea de subscript (hint/error) y no dos — subscriptSizing="dynamic" por defecto en los formularios, salvo donde el salto de layout moleste.
  • Halo de foco: el box-shadow: 0 0 0 3px var(--mat-sys-primary-container) actual se mantiene — sigue siendo válido y necesario ("mesón con luz variable"). Con campos más bajos gana protagonismo relativo, lo cual es deseable.
  • Densidad de appearance="outline": confirmar que el borde no se recorta con density -2 (bug histórico de Material en densidades bajas con outline). Si aparece, usar appearance="fill" o un padding mínimo de override.
  • Grilla de 2 columnas (.opt-form-grid): con campos de 44 px, el formulario de cliente (11 campos) entra en ~1 viewport sin scroll en escritorio. Mantener el colapso a 1 columna bajo 600 px.

06¿La marca da sensación de "amigable, sencillo pero robusto"?

Evaluación de la identidad v2.0 aplicada, contra los tres atributos pedidos.

AtributoQué lo sostiene hoyQué lo debilita hoyVeredicto
Robusto Añil profundo (#1B3A66/#2F5D8A) = serio, confiable, "de sistema". IBM Plex (diseñada para producto técnico). Monoespaciado para RUT/folios/montos. Rampa de estado semántica de un solo matiz. Contrastes AA/AAA verificados. Nada relevante. Es el atributo mejor cubierto. Logrado
Sencillo Paleta corta y disciplinada. Un solo botón primario por vista. Estados vacíos/de error con componente único. Navbar horizontal claro. La densidad y el tamaño (todo §2–§5). La banda primary-container plena en cada cabecera de tabla añade peso visual. Encabezados a 27 px en pantallas de trabajo. Parcial — lo arregla esta propuesta
Amigable Radios pill en botones/chips. Tono de voz cercano (tuteo interno). Terracota cálido en la paleta. Fraunces (serif humanista) en el login. El accent terracota se usa tan poco que en la práctica la interfaz de trabajo es azul-gris monocroma. Fraunces no aparece nunca fuera del login: la "calidez" no viaja al resto de la app. Mucho gris neutro en textos secundarios. Subrepresentado
Síntesis: la base de marca es sólida y comunica bien "robusto + confiable". "Sencillo" no falla por la paleta sino por el tamaño/densidad — se resuelve con §2–§5. "Amigable" está diseñado pero apenas se expresa: el acento cálido casi no se ve y el gesto humanista está encerrado en el login.

Recomendaciones de marca (bajas, no urgentes)

  • Cabecera de tabla más liviana: en lugar de fondo primary-container pleno, usar surface con un borde inferior de 2 px en primary-light y el texto en primary-dark. Mantiene la marca, quita peso. (Alternativa conservadora: primary-container al 50 % de opacidad.)
  • Dejar respirar el terracota en 2–3 puntos más, siempre "un trazo, no un relleno": el mat-hint de campos obligatorios pendientes, el ícono de la acción primaria de cada listado, el borde de foco de la fila seleccionada. Nunca como fondo de superficie.
  • Un toque de Fraunces fuera del login: solo en el título de app-empty-state y en la pantalla 404 / sin-permiso. Un guiño humanista en momentos "de pausa", nunca en tablas ni formularios.
  • Estados vacíos con voz: "Todavía no hay clientes cargados" en vez de "Sin datos". Ya está el componente; es solo copy.
  • No tocar: paleta, familias tipográficas, tagline, logo, tono de voz, rampa de OPT_EstadoOT. Están bien y ya validados internamente.

07Tokens y overrides propuestos

Todo concentrado en 2 archivos. Ningún .scss de feature cambia (mismo patrón que el halo de foco y .opt-badge-clinico ya existentes).

styles.scss

// 1) Densidad global en el mat.theme()
html {
  @include mat.theme((
    color: ( theme-type: light, primary: theme.$primary-palette, tertiary: theme.$tertiary-palette ),
    typography: 'IBM Plex Sans',
    density: -2,        // era 0
  ));

  // 2) Escala tipográfica compacta v2.1 (roles M3)
  --mat-sys-body-large:   400 14px/20px 'IBM Plex Sans';
  --mat-sys-body-medium:  400 13.5px/19px 'IBM Plex Sans';
  --mat-sys-body-small:   400 11.5px/16px 'IBM Plex Sans';
  --mat-sys-label-large:  500 13px/18px 'IBM Plex Sans';
  --mat-sys-title-medium: 600 15px/22px 'IBM Plex Sans';
  --mat-sys-title-large:  600 19px/26px 'IBM Plex Sans';
}

// 3) Densidad extra solo en tablas
.mat-mdc-table { @include mat.table-density(-3); }

// 4) Excepción móvil: input a 16px para evitar auto-zoom de iOS
@media (max-width: 599.98px) {
  .mat-mdc-form-field { --mat-sys-body-large: 400 16px/22px 'IBM Plex Sans'; }
}

// 5) Encabezados "desnudos" §4 — bajar un escalón
h1:not([class]) { font-size: 1.5rem;  } // 27 → 24
h2:not([class]) { font-size: 1.1875rem; } // 21 → 19
h3:not([class]) { font-size: 0.9375rem; } // 16.5 → 15

// 6) Cabecera de tabla más liviana (opcional, recomendación de marca)
.mat-mdc-table .mat-mdc-header-row { background: var(--mat-sys-surface); }
.mat-mdc-table .mat-mdc-header-cell {
  color: var(--mat-sys-primary);
  border-bottom: 2px solid var(--mat-sys-primary);
}

page-header.scss

.page-header        { margin-bottom: var(--opt-space-md); } // era --opt-space-lg (24 → 16)
.page-header__titulo{ font-size: 1.5rem; }              // era 1.6875rem (27 → 24)

shell.scss

.contenido { padding: 20px; } // era 24px; el @media <600px queda en 16px

Los valores de font shorthand y los nombres de custom properties deben confirmarse contra la salida real de mat.theme() en Angular Material 21 antes de aplicar. Si el proyecto ya usa sass aislado para verificar (como en la sesión v2.0), ese mismo método sirve para validar esta escala.

Riesgos y mitigaciones

  • Bug de appearance="outline" en densidades bajas (borde/label recortados) → si aparece, appearance="fill" o density -1 solo en form fields.
  • Budget de angular.json — esta propuesta no agrega un tercer set de tokens (solo sobrescribe valores), el impacto en tamaño de CSS es marginal.
  • Regresión visual en .spec.ts — los tests actuales no asertan sobre tamaños; no deberían romperse. Confirmar igual.
  • Percepción del equipo — cambio notorio. Mostrar el antes/después (esta página, §8) antes de mergear.
