Cómo se obtienen los Deudores en el Legacy

Análisis de old/Fuente y old/BD · módulo OrdenTrabajo/Deuda · 7 oct 2026

Resumen. El listado de deudores lo calcula el procedimiento almacenado sp_ListaDeudores (y su detalle, sp_DetalleDeudores). El script SQL sí existe en old/BD/Create_Procedure.sql. Una OT es «deuda» cuando OPT_OrdenDeTrabajo.EstadoPago = 'PENDIENTE'. La deuda de cada empresa es Σ Saldo − Σ Pagos, donde Saldo = Precio − Abono queda guardado en la OT y los pagos posteriores viven aparte en OPT_Pago. La resta de pagos se hace en la vista Razor, no en el SP.

2. Script SQL

Ubicación: old/BD/Create_Procedure.sql (codificación UTF-16 LE; hay que abrirlo así o convertirlo). Base: db_a25cfd_opt2, generado el 20-02-2026. Líneas 462-570 del archivo convertido.

2.1 sp_ListaDeudores — una fila por empresa

CREATE PROCEDURE [dbo].[sp_ListaDeudores]
AS
BEGIN
	DECLARE  @TEMP TABLE
		(idEmpresa INT, Empresa NVARCHAR(100),
		 Precio decimal, Abono decimal, Saldo decimal, Pagado decimal, OT INT)

	INSERT INTO @TEMP
	Select    A.idEmpresa
			 ,B.Empresa
			 ,A.Precio as Precio
			 ,A.Abono  as Abono
			 ,A.Saldo  as Saldo
			 ,(Select ISNULL(SUM(Monto),0) FROM OPT_Pago as D where D.idOt = A.idOt ) AS Pagado
			 ,1 as OT
	FROM OPT_OrdenDeTrabajo  as A
	INNER JOIN OPT_Empresa  AS B ON A.idEmpresa = B.idEmpresa
	WHERE A.EstadoPago = 'PENDIENTE'

	SELECT idEmpresa, Empresa,
		   SUM(Precio) as Precio, SUM(Abono) as Abono, SUM(Saldo) as Saldo,
		   SUM(Pagado) as Pagado, COUNT(OT) as OT
	FROM @TEMP
	GROUP BY idEmpresa, Empresa
	ORDER BY Empresa

	-- (versión anterior comentada: LEFT JOIN OPT_Pago + SUM(Precio)... )
END

2.2 sp_DetalleDeudores @idEmpresa — una fila por OT pendiente

CREATE PROCEDURE [dbo].[sp_DetalleDeudores] ( @idEmpresa INT )
AS
BEGIN
	Select A.idEmpresa, C.Empresa, B.RutCliente, B.Nombre, A.Beneficiario,
		   A.idOT, A.FechaAtencion, A.Precio, A.Abono, A.Saldo, A.NumeroCuota
		  ,CASE WHEN A.NumeroCuota = 0 THEN 0
		        ELSE CONVERT(INT,(A.Saldo / A.NumeroCuota)) END as ValorCuota
		  ,(Select COUNT(1) FROM OPT_Pago as D where A.idOT = D.idOT) as CuotasCanceladas
		  ,CASE WHEN A.NumeroCuota = 0 THEN A.Saldo
				ELSE ISNULL((Select SUM(ISNULL(D.Monto,0)) FROM OPT_Pago as D where A.idOT = D.idOT),0)
			END as MontoCancelado
		  ,CASE WHEN A.NumeroCuota = 0 THEN 0
				ELSE (A.Saldo - ISNULL((Select SUM(ISNULL(D.Monto,0)) FROM OPT_Pago as D where A.idOT = D.idOT),0))
			END as TotalDeuda
		  ,A.EstadoPago as Estado
		  ,B.Celular
	FROM  OPT_OrdenDeTrabajo  as A
	INNER JOIN OPT_Cliente AS B ON A.RutCliente = B.RutCliente
	INNER JOIN OPT_Empresa AS C ON A.idEmpresa  = C.idEmpresa
	WHERE A.EstadoPago = 'PENDIENTE'
	  AND A.idEmpresa = @idEmpresa
	ORDER BY A.idOT
END

3.2 Cómo se llega a «PENDIENTE» y a «PAGADO»

MomentoArchivoRegla
Al completar la OTIngresoController.cs:893-897Saldo = Precio − Abono; EstadoPago = Saldo > 0 ? "PENDIENTE" : "PAGADO". Si hay saldo y NumeroCuota = 0 lanza «Debe ingresar número de cuotas».
Pago individualPagoController.cs:90-103Inserta OPT_Pago; recalcula Precio − (ΣPagos + Abono); si es ≤ 0 pasa a PAGADO. Saldo de la OT no se modifica.
Pago masivo (Excel)PagoController.cs:225-265Solo OT pendientes de la empresa. Rechaza si monto > Saldo − ΣPagos. Si ΣPagos ≥ Saldo → PAGADO. Registra siempre TipoPago = "TRANSFERENCIA" y agrega bitácora «Entregado / Se realiza Pago Masivo» si aún no estaba entregada.

3.3 Fórmulas

Saldo (guardado en OT)   = Precio − Abono                  -- se fija al ingresar; los Pagos NO lo reducen
Pagado (por OT)          = Σ OPT_Pago.Monto
Deuda vigente (por OT)   = Saldo − Pagado                  -- calculada en la vista Razor
Deuda por empresa        = Σ Saldo − Σ Pagado   (solo OT con EstadoPago = 'PENDIENTE')
Valor cuota (detalle)    = INT(Saldo / NumeroCuota)
Dónde se resta realmente: en Deuda/Index.cshtml, SaldoPendiente = long.Parse(Item.Saldo) − long.Parse(Item.Pagado); el total del pie es la suma de esos valores. El SP entrega Saldo y Pagado por separado.

4. Hallazgos y particularidades

1. El detalle y el listado no cuadran

La pantalla de detalle (_ModalDetails) muestra y totaliza Saldo (bruto, sin descontar pagos), mientras el listado muestra Saldo − Pagado. Una OT parcialmente pagada se ve distinta en ambas pantallas. La columna TotalDeuda del SP existe, pero la vista no la usa.

2. Caso NumeroCuota = 0 inconsistente en el detalle

En sp_DetalleDeudores, si NumeroCuota = 0 entonces MontoCancelado = Saldo y TotalDeuda = 0: una OT pendiente figura como «deuda cero». El listado, en cambio, sí la cuenta completa. El alta normal lo impide, pero el pago masivo y los datos históricos pueden producirlo.

3. Las OT sin empresa no aparecen

Ambos SP usan INNER JOIN OPT_Empresa. Las OT de clientes particulares (idEmpresa nulo) con saldo pendiente nunca figuran como deuda. El detalle además exige existir en OPT_Cliente. Nota: el sistema nuevo sí las incluye (una fila con empresaPublicId = null).

4. Se confía en EstadoPago como bandera

Es texto libre, actualizado en tres lugares del código. Si un pago no pasa por esos flujos, la bandera queda desactualizada. El SP no verifica el saldo real (Saldo − Pagado > 0) ni el estado de la OT en bitácora, así que una OT anulada con PENDIENTE seguiría contándose.

5. Cuotas y mora: no existen en el cálculo

OPT_Cuota (con vencimientos y estado) no interviene. «Cuotas canceladas» se estima como COUNT(OPT_Pago), o sea 1 pago = 1 cuota; no hay noción de vencida/en mora. ValorCuota se trunca a entero.

6. Por qué existe la tabla temporal

La consulta original (comentada al final del SP) hacía LEFT JOIN OPT_Pago y luego SUM(Precio): con N pagos por OT, el precio, abono y saldo se multiplican por N. El rediseño con subconsulta por OT evita ese error. Cualquier reimplementación debe respetar esto.

7. Detalles menores

  • El contador «Deudores» del Home cuenta empresas, no OT ni dinero.
  • Las columnas decimal del @TEMP sin precisión equivalen a decimal(18,0): ok para pesos chilenos, truncaría decimales.
  • El listado carga todas las empresas de una vez, sin paginar ni filtrar por sucursal.

Coincide con lo que ya anotó CLAUDE.md: la migración M004 recalculó Saldo como abonos + pagos porque el legacy dejaba 3.472 OT con el saldo inflado. Eso es consecuencia directa del punto 3.3 de este informe.

Consulta equivalente en una sola pasada (referencia, para validar contra el legacy)

SELECT o.idEmpresa, e.Empresa,
       COUNT(*)                          AS OT,
       SUM(o.Precio)                     AS Precio,
       SUM(o.Abono)                      AS Abono,
       SUM(o.Saldo)                      AS Saldo,
       SUM(ISNULL(p.Pagado,0))           AS Pagado,
       SUM(o.Saldo - ISNULL(p.Pagado,0)) AS DeudaVigente
FROM OPT_OrdenDeTrabajo o
INNER JOIN OPT_Empresa e ON e.idEmpresa = o.idEmpresa
OUTER APPLY (SELECT SUM(Monto) AS Pagado FROM OPT_Pago WHERE idOT = o.idOT) p
WHERE o.EstadoPago = 'PENDIENTE'
GROUP BY o.idEmpresa, e.Empresa
ORDER BY e.Empresa;
